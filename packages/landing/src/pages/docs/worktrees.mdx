A Git worktree is another checked-out folder belonging to the same repository. Separate worktrees let independent tasks edit different folders and branches.

## Choose the working context before sending

The branch/worktree selector describes where the next task runs. Available choices depend on the selected branch and existing checkouts.

| Choice                           | Result                                                                   | Good use                                                     |
| -------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------ |
| New worktree                     | A separate folder and task branch                                        | Independent implementation or parallel work                  |
| Reuse worktree                   | An existing live checkout                                                | Review, rescue, or continuation of the same uncommitted work |
| Project folder / no new worktree | Work in the project's existing folder, with the selected branch behavior | Deliberate work in the current checkout or non-Git folder    |

Some flows also create a new branch in the project folder. Read both the branch and folder choice; a new branch alone does not create another checkout.

A branch change or new branch can be deferred until the first prompt starts setup. Its pending state stays visible. New task branch naming can use the name generated from that first prompt.

## Reuse a referenced conversation

Type `@@` in the composer, choose a conversation, and use its offered worktree-reuse action when you need that exact checkout. Check the resulting branch/worktree controls before sending.

Shared worktrees mean shared files. Two conversations can inspect the same uncommitted changes, but concurrent edits can interfere. [Fork](../rewind-and-fork/) also shares the source worktree; it is a conversation branch rather than a new Git checkout.

## Setup commands and progress

Project settings can define setup commands for new worktrees. Commands run in an interactive login-shell environment. Setup status and output appear in the conversation title block; output persists across reopen, reconnect, and service restart.

An interrupted or failed setup shows an error and can be retried. Resolve that error before expecting the agent to work in the intended checkout.

The selected source branch remains the task's comparison target. It does not automatically become `main` when setup finishes.

## How tools use the checkout

- Editor's tree and file operations use the conversation's working folder.
- Terminals start there; idle shells can move when a new worktree is created, while busy shells remain running with a warning.
- Git status, diffs, and branch history use the task's checkout and target.
- Browser tabs belong to the conversation, so its preview stays attached to that task.

## Archive and cleanup are separate decisions

Archiving preserves conversation history and moves it out of active lists. The dialog can include related parent/descendant conversations and shows their counts.

When applicable, separate options remove the worktree, remove the branch, or kill terminals. The interface checks Git state and warns about unmerged branches, local changes, and residual folders. Review every selected option before confirming.

Deleting an archived conversation is permanent. Do not infer folder or branch removal solely from whether the conversation was active or archived; use the options shown.

## Boundaries

A worktree is a Git organization mechanism. Provider access modes and sandbox policies determine what an agent may access beyond it.
