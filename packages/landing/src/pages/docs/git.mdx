In Cadencr, Git is visible because it helps you stay oriented: what changed, where those changes live, and what to do next.

## Why Git appears so much in Cadencr

Cadencr is built around **feature-based work**. That means one task gets its own little working area, usually with its own branch and Git history.

Why do that? Because it keeps work tidy:

- one feature does not casually spill into another,
- agent changes stay reviewable,
- you can check what happened before you commit to it, and
- merging finished work back in feels deliberate and easier to review.

A few Git concepts show up directly in the Cadencr interface:

| Term   | Plain-English version                              | Why you care in Cadencr                                                |
| ------ | -------------------------------------------------- | ---------------------------------------------------------------------- |
| Branch | A separate lane for one piece of work              | Each feature can stay focused instead of tangling with everything else |
| Commit | A saved checkpoint with a message                  | It is the moment you say, “Yes, this set of changes belongs together”  |
| Diff   | The before/after view of a change                  | This is how you check what really changed, not what you hope changed   |
| Push   | Sending your branch to the remote repo             | Useful when you want to share or open a PR                             |
| Merge  | Bringing finished work back into the target branch | The “okay, ship this lane back into the main road” step                |

<DocCallout title="Gentle truth" variant="tip">
  In Cadencr, Git is mainly there to answer practical questions: what changed, what branch this work
  belongs to, and what the next step should be.
</DocCallout>

## What the Git tab helps you do

The Git tab is the calm, visual version of “so... what happened here?”

<DocScreenshotPlaceholder
  title="Git tab in a feature workspace"
  caption="A friendly place to review changed files, compare against the target branch, and decide whether the next step is commit, push, or merge."
/>

Inside the Git tab, Cadencr helps you:

- review changed files before you trust them,
- switch between **uncommitted changes** and **changes vs the target branch**,
- inspect the diff instead of guessing,
- see what branch you are on and what it is compared against,
- use header actions like **Commit**, **Push**, and **Merge** when the work is ready.

That last part matters. The app is trying to surface the next sensible Git action instead of making you hunt for it.

## Safe everyday Git workflow in Cadencr

If you want the least dramatic daily rhythm, this is a good one:

1. **Start work in a feature workspace.** Think “one task, one home base.”
2. **Let the agent work, or make edits yourself.** No Git action needed yet.
3. **Open the Git tab and review the diff.** This is your confidence step.
4. **Commit when the change makes sense as one unit.** A commit is just a checkpoint with a label.
5. **Push when you want the branch on the remote.** Helpful for sharing, backup, or opening a PR.
6. **Merge when the feature is actually ready.** Not when you are tired of looking at it.

A simple mental model helps here:

- **Git tab** = review and understand
- **Commit** = save this chunk of work
- **Push** = share this branch with the remote repo
- **Merge** = bring finished work back to the target branch

If your team cares about merge style, Cadencr has a **Git merge strategy** setting. If your team does **not** care, leaving the default alone is a completely respectable life choice.

<DocCallout title="Beginner-friendly rule" variant="note">
  If you are unsure what to do next, open the Git tab before opening a terminal. A visible diff is
  usually more helpful than jumping straight into terminal commands.
</DocCallout>
