# React #185 / issue #351 investigation

Date: 2026-10-26. Baseline: `f1db5f700` (`0.15.0`).
Issue: <https://github.com/merkr-software/CadencR/issues/351>.

## Conclusion

**The reported intermittent crash is not reproduced by the live-agent runs below.**
Do not close #351 on the strength of this change.

A separate, deterministic instance of the same React error was found in
`UntitledCodeMirrorEditor`. Its Zustand cursor selector allocated a new fallback
object whenever the requested tab was absent. Two regression tests fail with
`Maximum update depth exceeded` before the fix and pass afterwards.

The normal create/close-buffer UI path did **not** reproduce this crash before
the fix. The regression deliberately keeps the subscriber mounted while its tab
is absent; it proves the selector defect, not that production navigation reaches
that state. No captured component stack ties it to the issue's telemetry yet.

## Confirmed selector defect

In `packages/desktop/src/components/editor/UntitledCodeMirrorEditor.tsx`, the
previous selector returned `cursorPosition ?? { line: 1, col: 1 }` **inside**
`useEditorStore`. Repeated snapshots of an unchanged store therefore differed by
identity when the tab was missing. React's external-store consistency check kept
scheduling another render.

The failing test produced both:

```text
The result of getSnapshot should be cached to avoid an infinite loop
Maximum update depth exceeded
  getRootForUpdatedFiber
  enqueueConcurrentRenderForLane
  forceStoreRerender
  updateStoreInstance
```

The fix selects the stored position or `undefined`, and supplies the display
fallback **after** the hook returns. It preserves real cursor updates and does
not change scheduling, add a debounce, or suppress the error.

The defect exists in `v0.14.1` too. The file originated in `fd8b6f524`
(2026-05-24, free-buffer support). This is not evidence that all historical #185
reports have the same cause.

## Why the final stack frame is insufficient

The installed production React client updates `nestedUpdateCount` after a commit
when eligible update work leaves more update work pending. Its pending mask here
is `42` (Sync, InputContinuous and Default lanes). The next update can encounter
the guard in `getRootForUpdatedFiber`.

Consequently, a final `useNow` timer or `forceStoreRerender` frame identifies where
the guard fired, not necessarily the component that maintained the pending work.
Pending fiber names captured by the probe are investigation leads, not causal
attribution either.

The earlier streaming/layout fixes are already present in this checkout:

- `useStreamingMarkdownThrottle` publishes timer updates through `startTransition`.
- `FeatureLayoutShell` memoizes its flat layout.
- `TabContentRegistry` keys its visited-tab effect by stable tab IDs.

The investigation also inspected session hydration, stream coalescing, scroll
callbacks, Virtuoso's synchronous notifications, model-picker effects, and
external-store selectors. None of the live traces demonstrated a sustained loop
in those paths. The unit tests for `AgentStream` mock Virtuoso, so they cannot
exclude a browser measurement/scroll feedback loop.

## Repeatable production probe

With the worktree's dev stack running:

```sh
node packages/desktop/scripts/react-update-depth-probe.mjs
```

Open the URL printed by the command. It builds a **separate** readable production
renderer under `packages/desktop/public/react-depth-probe-<timestamp>/`, with the
usual service proxy. It changes neither installed React nor application source.

Filter the browser console by `CADENCR_REACT_DEPTH`. The probe records:

- Commit totals, depth histogram and maximum depth.
- Committed and pending lane masks.
- Pending fiber names and their last seven ancestors on a new maximum or every
  500 commits; output is capped at 60 fibers.
- A bounded history of 80 commits in a snapshot at depth 40, on a global error,
  or on reload. The depth trigger also covers errors caught by a React boundary.

It records no component props, state values or conversation content. It retains
React's normal scheduler and limit, but instrumentation and an unminified build
still affect timing. It intentionally refuses to build if the expected React
commit implementation changes. This is a local diagnostic build, not a release
configuration; generated assets must not be committed or shipped. Normal builds
refuse to run while `react-depth-probe-*` remains under `public/`: move the
generated directory outside `public/` after the investigation. The probe itself
disables public copying and can be run repeatedly.

The next useful evidence is a failing run with this probe plus the root error's
component stack. In particular, correlate any sustained pending fiber with the
preceding commits before changing clocks or applying transitions broadly.

## Separate environment failures

The worktree's existing `packages/service/cadencr.local.db` failed a read-only
`PRAGMA quick_check` with `Freelist: size is 0 but should be 3`. The service also
reported `database disk image is malformed` while appending deltas. Those initial
attempts were excluded from the valid stress runs. The old database was preserved
without repair or replacement. A new temporary database passed `quick_check`.

After the BETA native follow-up, reloading an observing renderer coincided with
a permission-mode request against a closed query. The service logged
`failed to set permission mode on active query ... stdin is closed`, and the UI
displayed `SDK_ERROR`. The renderer remained usable. This is a distinct backend
control/lifecycle failure, not a React #185 reproduction.

Local evidence is retained in `/tmp/cadencr-qa-351/`: before/after test logs,
`react-depth-console.json`, service logs, the fresh database, and
`electron-stream.jpg`. Logs and databases are not committed.

## Finish-job review (2026-10-27)

Three independent reviews covered reuse, quality and efficiency. Follow-up fixes:

- Reuse the JSON download helper, untitled-buffer predicate and inferred payload
  type; share error normalization between copied details and persisted reports.
- Keep the original report context when suppressing repeat crashes, so displayed
  IDs remain present in exports.
- Keep a toast host on the global crash screen and preserve the independent text
  log even when JSON history cannot be written.
- Coalesce editor summaries before scanning; synchronously flush pending editor
  state when capturing an error, and cancel pending work on cleanup.
- Reject normal builds containing retained probe output in `public/`; clean up
  archive staging directories and archive the same bytes used for hashing.
